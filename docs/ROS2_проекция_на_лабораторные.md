# Проекция лабораторных работ 1–6 на ROS 2

*Карта-конспект: где математика каждой лабораторной живёт в стеке виртуального
проектирования роботов (ROS 2 / Gazebo / Pinocchio / MoveIt). Составлено по
официальной документации Gazebo (Jetty LTS), ROS 2 Jazzy и Pinocchio 4.x.*

Общий принцип курса: **в каждой лабораторной формула реализуется руками в
NumPy, а в ROS 2-стеке та же формула работает в боевом режиме.** Проверка
понимания — убедиться, что симулятор и ваш Notebook выдают одни и те же числа.
Прикладные блоки в концах решений делают именно это.

## ЛР_01 — SE(3) и дерево систем координат → **tf2**

| Из работы | В ROS 2 | Комментарий |
|---|---|---|
| `Transform` (R\|t), `from_Rt`, `inverse` | `geometry_msgs/TransformStamped`, `tf2::Transform`, `pin.SE3` | одномерное соответствие, вплоть до порядка полей |
| словарь `PARENT` | дерево `/tf` | `robot_state_publisher` строит его из URDF автоматически |
| `lookup(a, b)` | `buffer.lookup_transform(a, b)`, `ros2 run tf2_ros tf2_echo a b` | и то и другое — композиция цепочки до корня и обратно |
| `world_from(f)` | накопление `TransformStamped` в `tf2::Buffer` | tf2 хранит дерево с временными метками — единственное реальное отличие |
| накопление ошибки композиций (зад. 7) | `tf2::TimeCache`, переэкстраполяция | tf2 защищается теми же трюками, что вы измеряли |

Częste формулы: `T_child_world = T_parent_child⁻¹` — ровно ваш `lookup`.
SVD-ортогонализация `R_noisy` (зад. 8) — стандартный шаг дисторта... 

SVD-ортогонализация `R_noisy`（зад. 8） — то, что tf2 doesn't need: сообщения
передают кватернион, а матрицу восстанавливает аналитически — потому в стеке
проблемы теневой «неортогональности» просто нет (см. ЛР_02).

**Живое демо** (в контейнере `ros2`, см. `docker/README.md`):

```bash
ros2 run robot_state_publisher robot_state_publisher \
  --ros-args -p robot_description:="$(cat /labs/docker/urdf/planar_3r.urdf)"
python3 /labs/docker/js_publisher.py              # аналог JointState от драйвера
ros2 run tf2_ros tf2_echo link_ee link_base   # == lookup('link_ee','link_base')
ros2 run tf2_tools view_frames                # == словарь PARENT
```

> `ros2 topic pub` для терминала 2 не годится: он шлёт JointState с нулевой
> меткой времени, который robot_state_publisher в Jazzy молча отбрасывает.
> Скрипт `js_publisher.py` ставит живую метку, как настоящий драйвер.

## ЛР_02 — SO(3), кватернионы → **geometry_msgs/Quaternion, exp3/log3**

| Из работы | В стеке | Комментарий |
|---|---|---|
| `so3_exp` / `so3_log` | `pin.exp3` / `pin.log3`; `tf2` использует кватернионы | exp/log — язык оптимизации на многообразиях: MoveIt-солверы делают шаги в касательном пространстве |
| `R_to_quat` — порядок (w, x, y, z) | `geometry_msgs/Quaternion` — поля (x, y, z, w) | один и тот же кватернион, другой порядок полей; источник ошибок №1 у новичков |
| вырождение углов Эйлера при θ→π/2 (зад. 4) | поэтому весь ROS-стек ориентацию **не** хранит углами Эйлера | gimbal lock — не теория, а причина дизайна сообщений |
| `slerp` (зад. 5) | `Eigen::Quaternion::slerp` — интерполяция ориентации в планировщиках | одинаковое постоянство угловой скорости |
| дрейф интегрирования (зад. 6) | нормировка кватерниона на каждом шаге — как `qn = qmul(qn, dq); qn /= ‖qn‖` | вывод лабораторной — буквально правило хорошего тона в стеке |

**Сверка в блоке**: `pin.exp3 == so3_exp` до машинной точности; кватернион
EGS-сообщения совпадает с вашим с точностью до знака (q и −q — один поворот,
зад. 3).

## ЛР_03 — модель камеры → **sensor_msgs/CameraInfo, Gazebo-сенсоры**

| Из работы | В стеке | Комментарий |
|---|---|---|
| `intrinsics(f, cx, cy)` → K | поле `k` в `sensor_msgs/CameraInfo`; `image_geometry::PinholeCameraModel` | K переезжает в сообщение пиксель-в-пиксель |
| `distort` (k1, k2, p1, p2) | поле `d`, `distortion_model: plumb_bob` | одна и та же модель «plumb_bob» |
| `project(K, R, t, X)` | репроекция в `image_pipeline`; кадр камеры привязан к /tf через `frame_id` (ЛР_01) | конвейер «мир → камера → пиксель» из задания 1 — на каждый кадр |
| `Z = f·B/d` (зад. 4) | `stereo_image_proc` → `depth_image_proc`; у правой камеры поле `P[3] = −f·B` | формула записана прямо в матрице проекции сообщения |
| σ_Z ~ Z²·σ_d/(f·B) (зад. 5, 6) | причина выбора большой базы у «серьёзных» стереоплат | ваш эксперимент с наклонами − то, что ограничивает дальность RealSense и Kineсtt |

**Gazebo**: камера настраивается полем зрения, связь одна строка:
`f = width / (2·tan(fov/2))` — для f=800, width=1280 → `horizontal_fov = 0.6747`.
Стереопара собирается двумя камерами на базе B и конвейером из таблицы выше.

## ЛР_04 — гомография, PnP, RANSAC → **ros2_aruco / fiducials (AR-трекинг ROS)**

| Из работы | В стеке | Комментарий |
|---|---|---|
| `dlt_homography` + нормировка (зад. 1–2) | `cv2.findHomography` с `cv2.RANSAC` внутри трекеров маркеров | нормализация точек (Хартли) — то, что вы измерили как «лучше в N раз», включена в библиотеку по умолчанию |
| `pose_from_homography` (зад. 3) | первый шаг AR: маркер на плоскости → поза камеры | h1, h2, h3 и λ — дословно в cv2 |
| `pnp_gauss_newton` (зад. 4) | `cv2.solvePnP` — уточнение позы по некопланарным точкам | ваш Гаусс—Ньютон сходится к тому же решению (блок сверяет) |
| `ransac_homography`, порог 3 пикс, `n_iters(eps,s,p)` (зад. 5–6) | `cv2.solvePnPRansac`, параметр `reprojectionError`, выбор `iterationsCount` | формула числа итераций из задания 6 — то, чем настраивают солверы в ROS-нодах |
| виртуальный куб поверх маркера | ровно цель всего AR-трекинга: `world → /tf маркера → наложение графики` | в ROS поза маркера публикуется в /tf — и предмет «дополненная реальность» замыкается на ЛР_01 |

## ЛР_05 — прямая кинематика → **URDF, robot_state_publisher, Pinocchio**

| Из работы | В стеке | Комментарий |
|---|---|---|
| `dh(a, α, d, θ)` — таблица DH | **URDF** — `<joint>`: origin (xyz, rpy) + axis + `<limit>` | URDF — «раскрученная» DH-таблица: один шарнир = один joint-элемент |
| `fk_ur5` / `fk_dh3` | FK в `robot_state_publisher` (KDL) и Pinocchio — те же матрицы | блок сверяет Pinocchio-FK с `fk_poe` до 1e-12 |
| SymPy-вывод + `lambdify` (зад. 3) | кодогенерация аналитической кинематики в C++ (IKFast, Pinocchio) | ваш эксперимент «cse быстрее ручного цикла» — то, зачем стеку аналитика |
| 2R-кольцо рабочей зоны (зад. 4) | MoveIt planning scene: рабочая зона и ограничения | площади/объёмы Монте-Карло — как оценивается досягаемость |
| `exp_se3` / PoE (зад. 6) | внутреннее представление Pinocchio: винты | произведение экспонент — «родной» формат библиотеки |

**URDF манипуляторов курса**: `docker/urdf/planar_3r.urdf` (l = 0.5, 0.35, 0.2 —
как в заданиях 6–7) и `docker/urdf/planar_2r.urdf` (из ЛР_06).

## ЛР_06 — обратная кинематика → **MoveIt 2 (KDL / Trac-IK / IKFast)**

| Из работы | В стеке | Комментарий |
|---|---|---|
| `ik2_newton(target, q0)` (зад. 3) | каждый IK-солвер MoveIt — Ньютон/Гаусс—Ньютон с якобианом | квадратичная сходимость, что вы измерили — стандарт солверов |
| `damp` — λ-регуляризация (зад. 5) | DLS (damped least squares) — режим по умолчанию у KDL/Trac-IK | ваша проверка «демпфирование ограничивает шаг у границы» — причина, почему он и нужен |
| бассейны притяжения (зад. 4) | «seeds» — начальные приближения солвера | от seed зависит, в какой локоть сойдётся ответ (локоть вверх/вниз — как в задании 2) |
| cond J → ∞ на границе (зад. 5) | MoveIt отклоняет недостижимые цели; Trac-IK перезапускает Ньютон из случайных seed'ов | наклон −1/2 в log-log, который вы вывели — граница рабочей зоны в числах |
| `least_squares` с bounds (зад. 6) | joint limits в IK-солверах | q₂ ∈ [0.05, π] — то же, что limits в URDF (ЛР_05) |
| ядро якобиана 3R (зад. 7) | нуль-пространство избыточных роботов | планировщик 7-DOF-руки двигает локтем («самомахание»), не двигая схват |

**Итог цепочки 05→06**: URDF (ЛР_05) → FK → /tf (ЛР_01) → цель схвата →
IK-солвер (ЛР_06) → траектория. Это и есть «спроектировать виртуального
робота и заставить его работать» — то, что в ROS 2 делает связка
`robot_state_publisher` + `MoveIt 2`, а в курсе — шесть лабораторных.

## Как это запускать

1. **Ноутбуки** — как обычно, ничего не изменилось; прикладные блоки в конце
   опциональны и без Pinocchio/OpenCV просто пропускаются.
2. **Docker-окружение** — `docker/docker-compose.yml`: `labs` (JupyterLab со
   стеком) и `ros2` (ROS 2 Jazzy с tf2-инструментами). Инструкции и команды
   для живых демо — в `docker/README.md`.
3. **Pinocchio локально** (macOS, arm64): `pip install pin` — ставится нативно,
   контейнер для блоков не обязателен.
